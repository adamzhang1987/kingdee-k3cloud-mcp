# 会话与鉴权代码 Review

> 审阅范围：`src/kingdee_k3cloud_mcp/server.py` 中的会话（K3Cloud SID）管理与 MCP Bearer Token 鉴权两条链路。
> 审阅基准：`kingdee-k3cloud-mcp` v1.3.2，依赖 `kingdee.cdp.webapi.sdk` 8.2.0、`mcp` 1.27.0（均按 `uv.lock` 锁定版本核对源码）。
> 结论性质：本文只记录问题与建议，**未修改任何实现代码**。
> 配套文档：[`session-auth-experiments.md`](session-auth-experiments.md) —— 三轮实证测试的完整流程、
> 探针方法论、逐轮数据与复现指南。本文中所有标注「实测」的结论，其原始过程与数据均在该文档。

## 结论摘要与证据等级

PR #15 评论中反馈的「会话信息已丢失，请重新登录」与 MCP 协议版本升级没有直接关系。就当前代码而言，最可疑的是会话恢复状态机本身：它会清空 cookie 后再次发送请求，但无条件丢弃第二次响应、返回第一次错误，并且在确认新 SID 是否有效之前就启动 300 秒冷却。

> **2026-08-29 两轮实测的结论（§4.0、§4.0-2）**：
> **「会话信息已丢失，请重新登录」根本不是会话错误，而是认证失败的通用错误**——用不存在的用户名或错误的 `app_secret` 会得到字节级相同的响应（`MsgCode=1`）。
> 两轮共 200 余次请求、7 种会话生命周期干预（空 SID、无效 SID、闲置 90 分钟、20 个并发同身份会话、4 路真并发、Web 端登录、登出）**全部无法复现**该错误。
> 第 3 轮（§4.0-3）用 A-B-A 对照把结论修正到位：**服务端在持有有效 SID 时根本不校验凭据，只有无会话时才回落到凭据校验**；该错误的准确含义是「无有效会话且重新认证失败」，14/14 可重复复现，判据 `MsgCode == 1` 经 4 类业务错误对照验证干净。
> 因此 300 秒冷却的前提被证伪，而整套 `RetryableK3CloudApiSdk` 恢复机制针对的是一个**不存在的故障模式**，应当删除而非修复（见 S3）。排查方向全部转向认证与授权配置。
> 附带一条运维含义：凭据出错会被有效 SID 长期掩盖，**重启 Server 会把偶发问题变成永久问题**。

本文使用以下证据等级，避免把源码推断写成已经证实的服务端事实：

| 等级 | 含义 | 本文中的典型结论 |
|------|------|------------------|
| **已确认：源码** | 可由仓库或锁定依赖源码直接证明 | 第二次响应被丢弃；写请求会被重放；恢复前设置冷却时间 |
| **已确认：离线复现** | 可用 mock / 单元测试稳定复现 | `_check_expired` 的异常响应崩溃路径 |
| **待确认：真实环境** | 依赖具体 K3Cloud 版本、网关、拓扑或客户端生命周期 | LB 是否要求粘性会话；会话丢失的真正成因 |
| **已确认：真实环境** | 已在生产账套用只读探针实测（§4.0） | 清 SID 后立即成功；SID **不需要**“激活”；无效 SID 被服务端静默换发 |

特别注意：SDK 每次生成 HMAC 签名是源码事实，但这**不能单独证明 SID 对所有 K3Cloud 部署都只是可选优化**。金蝶公开资料中既有第三方授权 SDK 的签名调用方式，也有业务请求必须携带登录返回 SID、`MsgCode=1` 后重新登录的说明。**在本项目当前账套上已实测确认 SID 只是续用凭证而非准入条件（§4.0）**，但换部署仍须重测。

## 2. 依赖侧事实（后续判断的依据）

除明确标注“推论/待实测”的内容外，以下均为直接读取锁定版本 wheel 源码得到的事实。

### 2.1 `kingdee.cdp.webapi.sdk` 8.2.0

- **该版本没有公开的 Login / ValidateUser 方法**。`WebApiClient.BuildHeader()` 每次请求都会重新计算 `X-Api-Signature` 与 `X-Kd-Signature`；这是源码事实。
- `BuildHeader()` 在本地 SID 非空时发送 `kdservice-sessionid`，为空时不发送；`FillCookieAndHeader()` 会保存服务端响应中的 SID。这只能证明 SDK 支持“无本地 SID 发起请求”和“回带服务端 SID”，**不能证明服务端业务接口完全无状态，也不能证明新 SID 无需激活**。
- **待真实环境验证**：清掉陈旧 SID 后，同一个签名业务请求是否会立即成功；第一次无 SID 请求是否下发可立即使用的新 SID；不同 K3Cloud 版本和负载均衡拓扑是否一致。
- `CookieStore.set_sid()` 仅在新值非空时覆盖，**永不清空**。因此陈旧 SID 只能靠整体替换 `cookiesStore` 来清除（现有代码正是这么做的，方向正确）。
- `WebApiClient.__init__` **无条件**设置 `self.cookiesStore = CookieStore()`。
- `WebApiClient.Execute()` 在 `initialize` 为 False 时是 `return RuntimeError(...)`——**返回**异常对象而非抛出。
- `PostJson()` 使用 `requests.post(..., verify=False)`，模块顶部还有 `urllib3.disable_warnings(InsecureRequestWarning)`：**TLS 证书校验被全局关闭**。
- `BuildHeader()` 中 `nonce = str(int(time.time()))`，与 timestamp 同值（同一秒内的两次请求 nonce 相同）。
- `K3CloudApiSdk.GetDataCenters()` 存在，从客户端接口语义看是只读操作。它是否会建立与动态表单业务接口相同且可用的 SID，**尚未验证**，因此当前只能作为候选探针，不能直接认定为可靠的会话重建接口。

### 2.2 `mcp` 1.27.0

- `func_metadata.call_fn_with_arg_validation`：同步 tool 函数**直接在事件循环中调用**（`return fn(**args)`），**不走线程池**。
- `FastMCP.sse_app()` / `streamable_http_app()` 在 **run 时**才读取 `self._token_verifier` 与 `self.settings.auth`；`FastMCP.__init__` 里的 auth 一致性校验只在构造时执行。
- `BearerAuthBackend.authenticate()` 仅在 `verify_token()` 返回真值时放行，并额外检查 `expires_at`。
- `FastMCP.Settings` 是 `BaseSettings(env_prefix="FASTMCP_", env_file=".env")`——`.env` 中的 `FASTMCP_HOST` / `FASTMCP_PORT` 由 pydantic-settings 自行读取，**不依赖** `setup()` 里的 `load_dotenv()`。
  （曾怀疑这里因为 `load_dotenv` 晚于 `FastMCP()` 构造而失效，核对后**排除**，不是问题。）

## 3. 问题清单

### 3.1 严重 —— 会导致数据错误或崩溃

#### S1. 会话恢复会重放原始写请求，产生不可接受的副作用不确定性

- **位置**：`server.py:112-114`
- **现象**：检测到会话丢失后，代码用**原样的 `service_name` + `json_data`** 再打一次请求，结果丢弃，目的仅是拿新 SID：

  ```python
  super().Execute(
      service_name, json_data, invoke_type
  )  # establishes SID, result discarded
  ```

  而 `Execute` 是所有 tool 的公共出口，`save_bill` / `submit_bill` / `audit_bill` / `unaudit_bill` / `delete_bill` / `execute_operation` / `push_bill` **全部**经过这里。
- **影响**：第二次请求携带完整 HMAC 签名，服务端可能鉴权通过并真正执行保存 / 审核 / 删除 / 下推，但调用方只收到第一次的「会话丢失」错误。通常会话校验应发生在业务操作之前，因此不能仅凭现有证据断言第一次请求已经执行、必然形成“双份单据”；但是客户端无法证明第一次请求没有产生副作用，也无法观察第二次请求的结果。这属于非幂等操作的结果不确定性，已经足以判定为严重风险。
- **建议**：绝不为了获取 SID 而重放写业务负载。可以研究使用幂等只读探针，但 `GetDataCenters()` 能否建立业务接口可用 SID 必须先按 §4 的 T6 实测。若没有被目标 K3Cloud 明确支持的重新鉴权方式，写操作遇到会话丢失时应返回“结果未知、禁止自动重试”，由调用方查询单据状态后决定后续动作。

#### S2. `_check_expired` 有三条未捕获的 `AttributeError` 崩溃路径

- **位置**：`server.py:59-60`

  ```python
  errors = (data.get("Result") or {}).get("ResponseStatus", {}).get("Errors", [])
  return any(SESSION_LOST_MSG in (e.get("Message") or "") for e in errors)
  ```

  `Result` 用了 `or {}` 兜底，但 `ResponseStatus`、`Errors` 元素都没有。
- **实测**（按同一份逻辑复现，非推测）：

  | 响应形态 | 结果 |
  |---|---|
  | `{"Result":{"ResponseStatus":null}}` | **AttributeError** |
  | `{"Result":[{...}]}`（`Result` 是数组） | **AttributeError** |
  | `{"Result":{"ResponseStatus":{"Errors":["会话信息已丢失"]}}}`（`Errors` 元素是字符串） | **AttributeError** |
  | `{"Result":{"ResponseStatus":{"Errors":null}}}` | False（`TypeError` 被吞，可接受） |

- **影响**：`_is_session_expired` 的 `except` 只列了 `JSONDecodeError / TypeError / ValueError`，**`AttributeError` 会穿透**到 `RetryableK3CloudApiSdk.Execute`，使该次 tool 调用直接抛异常（FastMCP 包成 `ToolError`），而不是把金蝶原始错误透传给模型。`_check_expired` 被直接调用时更是裸崩。
- **建议**：逐层 `or {}` / `isinstance` 收敛；`except` 补 `AttributeError`；对 `Errors` 元素加 `isinstance(e, dict)` 过滤。

### 3.2 高 —— 影响可用性 / 安全姿态

#### S3. 整套会话恢复机制针对的是一个不存在的故障模式（应删除，而非修复）

- **位置**：`server.py:88`（`_RESET_COOLDOWN = 300`）、`98-119`
- **现状**：过期 → 清 SID → 再次发送同一请求 → **无条件丢弃第二次响应** → 返回第一次错误。现有测试甚至明确断言“第二次返回成功时仍应把第一次过期错误返回给调用方”（`tests/test_server.py:147-152`）。因此，会话过期后的当前调用必然失败，即使恢复请求已经成功。
- **冷却期的准确语义**：后续调用仍会先正常访问 K3Cloud；若新 SID 已经可用，它可以立即成功，并不会被冷却逻辑拦截。只有当后续调用继续返回会话过期时，代码才会因为仍在 300 秒内而跳过再次清 SID。因此它不是“无条件全线报错 5 分钟”。但如果恢复请求没有拿到有效 SID，调用会在冷却期内持续失败，300 秒后重复同一套恢复流程，故障可能无限循环，并非最长 5 分钟。
- **两轮实测把这条问题从「参数取错」升级为「机制本身不成立」**：
  1. **300 秒冷却的前提被证伪（§4.0）**：新 SID t=0 即可用，0/1/5/30s 摘要不变；空 SID 与无效 SID 都不会让请求失败。
  2. **触发条件根本不存在（§4.0-2 结论 8）**：「会话信息已丢失」实为**认证失败的通用错误**——用不存在的用户名或错误的 `app_secret` 会得到字节级相同的响应。两轮共 200 余次请求、7 种会话生命周期干预全部无法触发它。
- **第 3 轮在本账套上覆盖了三种情形（§4.0-3 结论 12、13）**，无一需要恢复逻辑：

  | 情形 | 实测结果 | 恢复逻辑有用吗 |
  |---|---|---|
  | SID 陈旧/无效/为空 + 凭据正确 | **直接成功**，服务端静默换发 SID | 不会触发，无从谈起 |
  | 有有效 SID + 凭据错误 | **直接成功**（服务端不校验凭据） | 不会触发 |
  | 无有效 SID + 凭据错误 | 「会话信息已丢失」 | **清 SID 重试仍然失败**——凭据错就是错 |

- **在本账套上，以上三种情形没有一种用得上恢复逻辑。** 但必须写明这个结论的边界：实测**从未构造出「服务端已知且被显式作废」的会话**——注入的是服务端没见过的随机 SID，自然过期的则被静默换发。因此不能断言该故障模式在所有部署上都不存在；多节点/LB 拓扑与其它 K3Cloud 版本仍未覆盖（见 experiments 文档 §10）。
- **删除恢复机制的依据不依赖上面那个全称判断**，而是两条各自独立成立的理由：
  1. **`_RESET_COOLDOWN` 的前提已被证伪**——新 SID t=0 即可用，300 秒这个数字没有任何事实依据；
  2. **为取 SID 而重放原始请求，对非幂等写操作本身就不安全**，与故障模式是否存在无关（这是通用安全约束，见 S1）。
  即便将来在别的部署上确实观察到「已知会话被作废」，正确的应对也不是恢复现在这套逻辑，而是针对实测到的行为重新设计——且写操作绝不能自动重放。
- **建议（已由实测确定）**：
  1. **删除整个会话恢复机制**，而不是修复它：`_RESET_COOLDOWN`、`_session_reset_at`、`cookiesStore` 重置、第二次 `super().Execute()` 全部移除。`RetryableK3CloudApiSdk` 可退化为不再需要的子类。
  2. 检测到 `MsgCode == 1`（§4.0-3 结论 14 已验证该判据干净）时，**原样透传给调用方**，并附诊断提示：这是认证/授权配置问题，自动重试无意义，需人工核对 **`KD_USERNAME` / `KD_APP_ID` / `KD_APP_SEC` / `KD_LCID`**（结论 13 实测这四项会产生此错误）与第三方登录授权状态。注意 **`KD_ACCT_ID` 错误不走这条路径**——它返回 HTTP 非 200，`PostJson` 直接抛 `RuntimeError`，应在提示中单列。
  3. 同步删除 `tests/test_server.py:147-152` 中「第二次成功也要返回第一次错误」的断言，以及所有围绕冷却期的测试；改为断言「该错误原样透传且不产生第二次请求」。
  4. S1（写请求重放）与 S4（恢复异常顶替原始错误）随恢复机制删除而**一并消失**，无需单独修复。
- **一条必须写进修复说明的运维含义（结论 12）**：凭据/授权出错会被一个仍然有效的 SID **长期掩盖**，直到会话失效或进程重启才爆发。因此「重启一下 MCP Server」不但不能修复，反而会把偶发问题变成永久问题——诊断提示里应当说明这一点。
- **残留的不确定性**：以上全部实测只覆盖本项目当前账套（单节点 IIS 8.5，无 LB 痕迹）。报障者若处在多节点/LB 环境或不同 K3Cloud 版本，仍可能有本部署测不出的行为；但即便如此，「清 SID 重试」对认证失败依然无效，删除的结论不受影响。

#### S4. 恢复调用的异常会顶替掉原始错误

- **位置**：`server.py:112-114`，未包 `try/except`
- **现象**：`PostJson()` 在非 200 时 `raise RuntimeError(res.text)`，`ValidResult()` 也会抛。恢复调用一旦抛异常，`Execute` 就走不到 `return result`，调用方拿到的是一个与真实问题无关的裸异常，而不是本该透传的「会话信息已丢失」。
- **附带**：`self._session_reset_at = now` 在恢复调用**之前**赋值（`server.py:105`），因此恢复失败也照样进入 300 秒冷却，而且代码没有检查新 SID 是否为空、是否变化。
- **建议**：捕获 SDK 明确定义的网络/协议异常，保留原始会话错误并记录恢复异常；不要用过宽的 `except Exception` 静默吞掉编程错误。恢复结果和 SID 变化应反过来决定状态机进入“已恢复”“等待”还是“恢复失败”。

#### S5. Bearer Token 使用 `==` 比较，非恒定时间

- **位置**：`server.py:47`

  ```python
  if token == self._key:
  ```

- **影响**：SSE / streamable-http 模式下这是暴露在网络上的静态密钥，也是**唯一**保护整套 ERP 读写工具的凭据。`==` 存在理论上的时序侧信道；在有网络抖动的远程场景中，实际可利用性通常较低，因此这是低成本安全硬化项，不应与 S6/S7 的 fail-open 风险等量看待。
- **建议**：改用 `hmac.compare_digest(token, self._key)`。一行改动，无副作用。

#### S6. 鉴权装配依赖 FastMCP 私有属性，未来版本可能静默降级为「无鉴权」

- **位置**：`server.py:891`

  ```python
  mcp._token_verifier = ApiKeyVerifier(api_key)
  ```

- **已核实**：在 mcp 1.27.0 下**确实生效**——`sse_app()` / `streamable_http_app()` 在 run 时才读该属性，赋值时机没问题。
- **风险**：`pyproject.toml` 允许 `mcp>=1.26.0,<2`。一旦上游重命名或移除该私有属性，`mcp.settings.auth` 虽被设置但 `self._token_verifier` 为 `None`，`sse_app()` 就**不会挂载** `AuthenticationMiddleware` / `RequireAuthMiddleware`——服务照常启动，运维以为有鉴权，实际完全裸奔。这是 **fail-open**。
- **附带**：该赋值绕开了 `FastMCP.__init__` 中的 auth 一致性校验。
- **建议**：注入前显式检查属性存在，缺失则**启动即失败**（fail-closed），并在文档中标注该写法与 mcp 版本绑定。更稳妥的方案是把 `FastMCP(...)` 的构造推迟到读取环境变量之后，走官方入参 `FastMCP(..., token_verifier=..., auth=...)`。

#### S7. 非 stdio 传输在未设 `MCP_API_KEY` 时静默零鉴权启动

- **位置**：`server.py:888-892`（`if api_key:` 之外没有任何提示）；`--mode` 默认 `readwrite`
- **影响**：`--transport sse` 且 `FASTMCP_HOST=0.0.0.0` 时，任何能连到该端口的人都可以调用全部**写**工具——保存 / 审核 / 反审核 / 删除 / 下推真实 ERP 单据。`.env` 里写成 `MCP_API_KEY=`（空字符串）同样被当作「不启用鉴权」，且没有任何提示。
- **建议**：非 stdio 传输且无 key 时打**醒目 warning**，或要求显式 `MCP_ALLOW_NO_AUTH=1` 才放行；key 读取后做 `.strip()`，拒绝空或纯空白值。

### 3.3 中 —— 健壮性 / 正确性瑕疵

#### S8. 会话过期只认一个中文字符串

- **位置**：`server.py:21` `SESSION_LOST_MSG = "会话信息已丢失"`
- **影响**：`KD_LCID` 是可配置项（`.env.example` 中就暴露了）。设成 1033（英文）时服务端返回英文提示，整套会话恢复机制**完全失效**，用户只会看到反复失败而不知原因。其它鉴权类错误（未登录 / 身份验证失败 / HTTP 401）也不在识别范围内。
- **判据已由实测定稿（§4.0-3 结论 14、15）**：
  - 14 次真实认证失败**全部** `MsgCode == 1` / `ErrorCode == 500`；
  - 4 类业务错误（表单不存在、字段不存在、非法过滤、空字段列表）的 `MsgCode` 分别是 4 / 9 / 4 / 8，**无一为 1** —— 判据干净，不会误伤业务错误；
  - `lcid=1033` 下消息**仍是中文**，`MsgCode` 仍为 1 —— 本条 S8 原本担心的多语言失效在本部署上**不成立**，但 `MsgCode` 仍是更稳的判据。
- **建议**：以 `MsgCode == 1` 为唯一主判据，消息串仅作日志佐证。判据的语义应正名为「**无有效会话且重新认证失败**」，而不是「会话过期」。

#### S9. 顶层 `ResponseStatus` 形态漏检

- **位置**：`server.py:59`，只查 `Result.ResponseStatus.Errors` 这一条固定路径
- **实测**：`{"ResponseStatus":{"Errors":[{"Message":"会话信息已丢失"}]}}` 返回 **False**（漏检）。
- **建议**：递归查找任意层级的 `ResponseStatus.Errors`，而不是写死路径。

#### S10. `_session_reset_at = 0.0` 与 `time.monotonic()` 的语义冲突

- **位置**：`server.py:92`（初值 `0.0`）、`server.py:98`（`now - self._session_reset_at >= self._RESET_COOLDOWN`）
- **现象**：如果当前平台的 `time.monotonic()` 值小于 300，`now - 0.0 < 300` 成立，首次会话过期会被误判为「处于冷却期」而跳过恢复。Linux 上该时钟通常与宿主机启动时间相关，而非容器启动时间，所以这不是每次新容器都必现；但 `0.0` 仍错误地把“从未重置”编码成了一个合法时间点。
- **建议**：初值改为 `None` 或 `float("-inf")`，用显式的「从未重置过」语义。

#### S11. `hasattr(self, "cookiesStore")` 是死分支

- **位置**：`server.py:106-111`
- **依据**：`WebApiClient.__init__` **无条件**设置该属性，且 `RetryableK3CloudApiSdk.__init__` 必然调用 `super().__init__()`。因此 else 分支的「SDK internals changed」告警**永远不会触发**——它营造了一种有防护的错觉，实际没有任何防护作用。
- **建议**：删掉该分支；若确实想防上游变更，改成有效的契约断言（例如 `InitConfig` 之后校验 `self.initialize is True`）。

#### S12. `MCP_ISSUER_URL` 默认值写死 8000，与 `FASTMCP_PORT` 不联动

- **位置**：`server.py:890`，默认 `http://localhost:8000`
- **影响**：改了 `FASTMCP_PORT` 却没同步 `MCP_ISSUER_URL` 时，`/.well-known/oauth-protected-resource` 与 401 响应中的 `WWW-Authenticate` 都会指向错误端口，遵循 OAuth 发现流程的客户端将连不上。`.env.example` 里两处示例（注释写 `127.0.0.1`、代码默认 `localhost`）也不一致。
- **建议**：默认值从 `mcp.settings.host` / `mcp.settings.port` 推导（`0.0.0.0` 归一化为 `127.0.0.1`），仍允许显式覆盖。

#### S13. `KD_LCID` 缺少解析保护

- **位置**：`server.py:902` `lcid=int(os.getenv("KD_LCID", "2052"))`
- **现象**：`.env` 中写成 `KD_LCID=`（空）或非数字，直接抛 `ValueError: invalid literal for int()`，启动失败且报错信息不指向具体配置项。相邻的 `KD_ORG_NUM` 有 `or "0"` 保护，`KD_LCID` 没有——两者不一致。
- **建议**：补 `or "2052"`，并用 `try/except` 转成明确的配置错误消息。

#### S14. `QUERY` 轮询模式可能在外层恢复逻辑接管前先解析失败

- **位置**：`server.py:94` 覆写 `Execute`；SDK 的 `ExecuteByQuery()` / `QueryTaskResult()` 内部直接调用 `PostJson()` 并解析 `Status`。
- **现状**：外层 `RetryableK3CloudApiSdk.Execute` 最终仍能检查 `super().Execute(...)` 的正常返回值，因此不能笼统说 QUERY 模式“完全绕过”恢复。但是如果 `PostJson()` 返回会话错误对象，`ExecuteByQuery()` 可能在返回外层前就因缺少 `Status` 等字段抛出 `KeyError`，外层检测没有机会运行。项目目前没有使用 `InvokeMethod.QUERY`，属于休眠风险。
- **建议**：记录该边界；未来启用 `BatchSaveQuery` 等轮询接口前，补充真实响应和异常路径测试。

#### S15. 多数写工具不做过期透传判断

- **位置**：`view_bill`(707)、`query_metadata`(719)、`save_bill`(740)、`submit_bill`(758)、`audit_bill`(776)、`unaudit_bill`(794)、`delete_bill`(812)、`execute_operation`(832)、`push_bill`(876) 都是直接 `return _sdk().Xxx(...)`
- **说明**：这些直接透传金蝶原始 JSON，模型能看到「会话信息已丢失」原文，**行为上可接受**；但与查询侧（`server.py:145` / `201` / `283` / `420` 有显式判断）不一致，模型拿到的是裸错误而非结构化提示。
- **建议**：列为可选提升——统一包一层错误归一化。⚠️ 归一化文案**不能**写成「会话恢复中，请稍后重试」：实测确认 `MsgCode == 1` 是**认证失败**，自动重试无效（S3、§4.0-3 结论 12）。正确的提示应指明这是认证/授权配置问题，并给出需核对的凭据字段。

### 3.4 低 —— 记录备查

#### S16. 依赖 SDK 全局关闭了 TLS 校验

`requests.post(..., verify=False)` + `urllib3.disable_warnings(InsecureRequestWarning)`：凭据签名在**未验证证书**的 TLS 通道上传输，中间人可劫持。这是上游 SDK 的行为，本项目在不覆写 `PostJson()` 的前提下无法修复。作为已知风险记录，建议在内网 / 受控网络环境部署。

#### S17. 同步 tool 阻塞事件循环（以及一条重要的连带约束）

已核实 mcp 1.27 的同步 tool 在事件循环中直接执行。

- **好消息**：当前**不存在** `cookiesStore` / `_session_reset_at` 的数据竞争——所有调用天然串行。
- **坏消息**：`query_bill_to_file` 这类翻页导出会把整个 server 阻塞数分钟；SSE 模式下所有客户端一起卡住，连 ping / 取消都处理不了。
- **⚠️ 连带约束**：若将来为解决阻塞而把 tool 改成 `async` + `anyio.to_thread.run_sync`，**必须同时给会话恢复段加 `threading.Lock`**。否则恢复逻辑会立刻变成真实竞态：多线程同时替换 `cookiesStore`，而且 `FillCookieAndHeader` 的 `cookies.clear()` 与 `BuildHeader` 的 `items()` 迭代会撞出 `RuntimeError: dictionary changed size during iteration`。

#### S18. 启动时不校验凭据

`setup()` 只检查 5 个环境变量非空，从不实际连一次金蝶。凭据错误要等到第一次工具调用才暴露。建议增加可选启动探针尽早验证凭据。

⚠️ **`GetDataCenters()` 已实测排除，不能用作凭据探针**（experiments 文档 §6 R7）：它是**免鉴权**接口——把 `app_secret` 或 `user_name` 改错，它照样正常返回数据中心列表。用它做自检会产生假阳性（凭据已经错了却报告"通过"）。探针必须使用真正走凭据校验的业务接口，例如一次最轻量的 `ExecuteBillQuery`。原 T6「验证它能否预热 SID」的计划因此作废。

#### S19. `_sdk()` 使用 `assert`

`python -O` 下断言会被剥离，`api_sdk` 为 `None` 时退化成语义不明的 `AttributeError`。建议换成显式 `raise RuntimeError`。

## 4. 必须通过真实 MCP Client 与 K3Cloud 环境确认的问题

单元测试只能证明当前 Python 状态机如何处理模拟响应，不能回答 K3Cloud 服务端是否会立即签发/接受 SID、MCP Client 是否反复重启 server、负载均衡是否保持节点等问题。本节用于实际联调确认。

### 4.0 已完成的实测：第 1 轮（2026-08-28）

直连 SDK 的一次性只读探针（生产账套，`BD_MATERIAL` 取 1 行，全程无写操作），
用于回答 T2 / T4 / T5 所依赖的核心问题：**新 SID 到底需不需要「激活时间」**。

| # | 阶段 | 操作 | 耗时 | SID 前 | SID 后 | 结果 |
|---|------|------|------|--------|--------|------|
| 1 | A | 空 SID 首请求 | 405ms | `<empty>` | `8d74d3ba` | **成功**，返回 1 行 |
| 2 | B | 注入无效 SID（`invalid-<uuid4>`） | 308ms | `669f30c9` | `8c699350` | **成功**，服务端直接换发新 SID |
| 3 | C0 | 复用刚下发的新 SID，t=0s | 1059ms | `8c699350` | `8c699350` | **成功** |
| 4 | C0 | 复用同一 SID，t=1s | 176ms | `8c699350` | `8c699350` | **成功** |
| 5 | C0 | 复用同一 SID，t=5s | 558ms | `8c699350` | `8c699350` | **成功** |
| 6 | C0 | 复用同一 SID，t=30s | 292ms | `8c699350` | `8c699350` | **成功** |
| 7 | C | 整体替换 `cookiesStore` 后 t=0s | 1496ms | `<empty>` | `1c1857a2` | **成功** |

（SID 一律只记 `sha256(SID)[:8]`。第 1–2 行的 `SID 前` 与上一行的 `SID 后` 不同，
是因为 A、B 之间服务端每次都会换发新 SID。）

**结论 1 —— 「新 SID 需要几分钟才能在服务端激活」被证伪。**
新下发的 SID 在 **t=0** 就可用，此后 1/5/30 秒摘要不变、连续成功。
`server.py:88` 注释里那句 `new SID takes several minutes to activate server-side`
在该部署上不成立，因此 **300 秒冷却期没有事实依据**，「丢弃第二次响应、让 SID 慢慢激活」
这一整套设计的前提同时失效。

**结论 2 —— 空 SID / 无效 SID 都不会导致请求失败。**
空 SID 首请求直接成功；塞一个完全无效的 SID 请求**照样成功**，服务端忽略它并换发新 SID。
这与 §2.1「每请求重算 HMAC 签名」的源码事实一致：该部署下 SID 是服务端下发的续用凭证，
不是业务接口的准入条件。

**结论 3（新发现，影响 T3 的做法）—— 无法用「注入无效 SID」复现「会话信息已丢失」。**
原计划把注入无效 SID 当作自然过期的可控替身，实测表明二者服务端行为不同：
无效 SID 被静默替换，根本不报会话丢失。因此 PR #15 反馈的错误**不是**「本地 SID 陈旧」这么简单，
成因仍未定位，只能靠自然过期（Phase D）或服务端日志复现。

**旁证（T9 的早期负面证据）**：探针进程与 MCP Server 进程同时持有同一授权身份的不同会话，
两边交替查询均正常，未观察到互相踢下线。

#### Phase D：自然过期对照（2026-08-28 22:35 → 2026-08-29 00:05）

先取真实 SID，随后每轮闲置 1800 秒、期间不发任何请求，共 3 轮：

| # | 操作 | 耗时 | SID 前 | SID 后 | 结果 |
|---|------|------|--------|--------|------|
| 1 | 取真实 SID（预热） | 321ms | `<empty>` | `ff5097a3` | 成功 |
| 2 | 闲置 1800s 后 | 854ms | `ff5097a3` | `b702054e` | **成功**（SID 被静默换发） |
| 3 | 闲置 3600s 后 | 267ms | `b702054e` | `b702054e` | **成功**（SID 未变） |
| 4 | 闲置 5400s 后 | 1194ms | `b702054e` | `ede9d3a9` | **成功**（SID 再次被换发） |

**结论 4 —— 累计闲置 90 分钟，一次都没复现「会话信息已丢失」。**
服务端在 SID 失效时的行为是**静默换发新 SID 并正常返回业务数据**，从不返回会话错误——
这与 Phase B 注入无效 SID 的结果完全一致。第 3 次 SID 未变、第 2/4 次换发，说明换发时机由服务端
自行决定，客户端无从预测，但**任何一种情况下请求都成功**。

**由此得到本轮最重要的判断：在该部署上，`RetryableK3CloudApiSdk` 的整个恢复状态机
从未、也无法被 SID 生命周期触发。** 300 秒冷却不只是「参数取值不对」，它位于一条实测中
根本走不到的路径上。

**局限（必须写明）**：以上全部结论只覆盖**本项目当前账套的这一个部署**。
报障者的 K3Cloud 版本、网关拓扑、授权配置可能不同，不能据此断言「任何部署都不会出现会话丢失」。

**仍缺的样本**：真实的会话丢失响应 JSON 至今**未能采集到**（S2 的异常形态、S8 的英文 LCID 响应
都还缺料）。既然 SID 途径走不通，下一步只能从服务端日志、或从报障者环境取样。

**复现方式**：探针脚本为一次性文件，按约定留在 scratchpad，未纳入仓库；
关键参数已记录于 §4.6，可据此重建。

### 4.0-2 第 2 轮实测：并发抢占假设（2026-08-29）

第 1 轮的盲区：注入的是**随机无效 SID**，服务端从没见过，当作“没有会话”直接建新的；而被踢掉或被清理的 SID 是**服务端已知且已失效**的，可能走另一条分支才报错。第 1 轮无法制造后者，所以复现不出来是**设计使然，不是证据**。

本轮主假设：**另一个程序 / 另一个用户用同一授权身份重新认证，使先前的会话在服务端失效。**

探针在第 1 轮基础上增加 HTTP 层观测（monkeypatch `k3cloud_webapi_sdk.core.webapi_client.requests.post`，只记状态码、响应头名称、节点标识，不记 cookie 值与完整 SID），并改用原生 `K3CloudApiSdk`，避免恢复逻辑掩盖现象。所有会话在同一进程内以彼此独立的 SDK 实例承载——服务端无从区分是否同进程；T24 用线程做真并发。

#### 已完成：T21a / T22 / T24（109 次请求，全部只读）

| 测试 | 干预 | 结果 |
|---|---|---|
| 控制相 | A 单独活跃 5 次 | SID 稳定 |
| **T21a** | A、B 两个稳定会话交替请求 10 轮 | 双方各自 SID 全程不变，**共存无冲突** |
| **T22** | 另建 18 个同身份会话（累计 2/5/10/14/18 各检查一次 A） | A 的 SID `1f73fdf0` **纹丝不动**，无一次失效 |
| **T24** | 4 个会话线程级真并发 × 15 轮 | 全部成功，无 SID 换发 |

**总计：会话丢失 0 次，SID 换发 0 次。**

**结论 5 —— H1a（会话池上限挤掉旧会话）与 H1b（同一 user_name 单会话、新建即踢旧）在 N≤20 时均被否定。**
同一授权身份可以同时持有至少 20 个互不干扰的会话；并发请求也不会互相覆盖。
结合 S17 已确认的“同步 tool 在事件循环中串行执行”，**进程内并发覆盖同样排除**。

**结论 6（D3 相关）—— 该部署无负载均衡痕迹。**
响应头只有 `Server: Microsoft-IIS/8.5`，无任何 LB 亲和性 cookie（无 `ARRAffinity` / `BIGipServer*`）；
`KD_SERVER_URL` 是内网穿透域名，指向单节点。**因此 D3 在本部署上没有适用条件——
但这恰恰意味着，报障者若处在多节点/LB 环境，会有本部署根本测不出的行为。**

#### 结论 7（新发现，对应长期挂起的 T8）：SDK 的 Set-Cookie 解析不符合 RFC

`FillCookieAndHeader`（`.venv/.../core/webapi_client.py:135-142`）用 `headers['Set-Cookie'].split(',')` 切分，
而 cookie 的 `expires` 值本身含逗号（`Thu, 28-Aug-2026 ... GMT`）。实测服务端实际存下的是：

| 存储 key | `name` | `path` |
|---|---|---|
| `'kdservice-sessionid'` | `'kdservice-sessionid'` | `''`（丢失） |
| `' ASP.NET_SessionId'` | `' ASP.NET_SessionId'`（**带前导空格**） | `''`（丢失） |

`BuildHeader` 据此拼出的回带头为 `Theme=standard;kdservice-sessionid=…; ASP.NET_SessionId=…`。
在本部署上**碰巧可用**——名字里的前导空格恰好充当了 RFC 6265 要求的 `; ` 分隔空格；
`path` 丢失也不影响，因为 SDK 自己拼 Cookie 头、不做路径匹配。

这属于**上游 SDK 缺陷**，本项目无法直接修复，但应记录：一旦服务端改变 Set-Cookie 的顺序或格式，
或网关对畸形 Cookie 头更严格，这条路径就会失败，且失败形态很可能正是「会话信息已丢失」。
这是目前**唯一一条既有实据、又能解释环境差异**的候选成因。

#### 结论 8（决定性发现）：「会话信息已丢失」根本不是会话错误，而是**认证失败的通用错误**

用错误的凭据发起同一个只读查询，得到的响应与报障信息**字节级相同**：

| 干预 | 响应 |
|---|---|
| 不存在的用户名（`__no_such_user__`） | 「会话信息已丢失，请重新登录」 |
| 错误的 `app_secret`（32 个 `0`） | 「会话信息已丢失，请重新登录」 |

```json
[[{"Result":{"ResponseStatus":{"ErrorCode":500,"IsSuccess":false,
  "Errors":[{"FieldName":null,"Message":"会话信息已丢失，请重新登录","DIndex":0}],
  "SuccessEntitys":[],"SuccessMessages":[],"MsgCode":1}}}]]
```

> ⚠️ **本结论已由第 3 轮修正，见 §4.0-3 结论 12**：准确的表述是「没有有效会话，且重新认证失败」——
> 服务端在持有有效 SID 时根本不校验凭据。下文的判断方向不变，但适用条件需按结论 12 理解。

**这一条解释了此前所有实测结果为什么全是阴性**：两轮共 200 余次请求、7 种会话生命周期干预
（空 SID、无效 SID、闲置 90 分钟、20 个并发会话、4 路真并发、Web 端登录、登出）全部无法复现，
是因为**这个错误从来就与会话状态无关**。金蝶用了一个严重误导的错误文案：它的真实含义是
「本次请求没有通过身份认证」，`MsgCode=1` 即「需要重新建立身份」。

**由此推翻 `RetryableK3CloudApiSdk` 的根本前提**：清 SID 后重试，对认证失败**不可能有任何帮助**——
凭据错就是错，重试一万次还是同一个错。结合第 1 轮已证明的「SID 为空或无效根本不产生此错误」，
可以确定：**该恢复机制针对的是一个不存在的故障模式。**

### 4.0-3 第 3 轮：坐实并**修正**结论 8（2026-08-30）

结论 8 原本只有 2 次请求作依据，且那两次用的都是**全新、SID 为空**的实例。第 3 轮做 A-B-A 对照后
发现这个细节是关键的，结论 8 的表述需要修正。

#### 结论 12（修正结论 8）：服务端的认证优先级是「有 SID 就放行，无 SID 才校验凭据」

R5，同一实例上的四步（每步一次只读请求）：

| 步骤 | 状态 | 结果 |
|---|---|---|
| ① 好凭据建会话 | SID 已建立 | 成功 |
| ② **改坏 `app_secret`，保留 SID** | 坏凭据 + 有效 SID | **成功** ← 关键 |
| ③ **清空 `cookiesStore`**，凭据仍坏 | 坏凭据 + 空 SID | **会话信息已丢失** |
| ④ 复原凭据，SID 仍空 | 好凭据 + 空 SID | 成功 |

R1 另以 3+3+3 次请求复核了 ②：持有有效 SID 时把 `app_secret` 换成 32 个 `0`，**连续 3 次全部成功**。

> **2026-08-30 补充修正**：更准确的表述是「**SID 对应有效会话时**才放行」——
> 认证失败时服务端也会下发一个 SID，但那是空壳，带着它的请求仍会回落到凭据校验。
> 两个推论：认证失败不会锁死（每次都在用当前凭据重新尝试）；修复金蝶端配置后
> **无需重启**即自动恢复，只有改 `.env` 才需重启。详见 experiments 文档。

**因此该错误的准确含义是「没有有效会话，且重新认证也失败」**，而不是笼统的「凭据错误」。
服务端在有有效 SID 时**根本不校验签名**；只有在没有会话时才回落到凭据校验。

**这条修正带来一个重要的运维含义**：凭据/授权一旦出错，**可以被一个仍然有效的 SID 长期掩盖**，
直到会话失效或进程重启才突然爆发。这正好解释了「昨天还好好的、代码一行没改就坏了」这种间歇性表现，
也意味着**重启 MCP Server 会让问题从"偶发"变成"永久"**（新进程没有 SID，必须走凭据校验）。

#### 结论 13：凭据字段矩阵（全新实例 / 空 SID，各 3 次）

| 字段 | 结果 | MsgCode |
|---|---|---|
| `KD_USERNAME` | 会话信息已丢失 ×3 | 1 |
| `KD_APP_ID` | 会话信息已丢失 ×3 | 1 |
| `KD_APP_SEC` | 会话信息已丢失 ×3 | 1 |
| `KD_LCID`（无效值 9999） | 会话信息已丢失 ×3 | 1 |
| `KD_ORG_NUM`（999999） | **成功** ×3 | — |
| `KD_ACCT_ID` | **HTTP 非 200 → `RuntimeError`** ×3，消息 `Fail to verify thirty passport` | — |

12/12 一致复现，可重复性成立。两条例外都有意义：
`OrgNum` 参与签名但服务端不校验其有效性；**`acct_id` 错误走的是完全不同的路径**——
HTTP 非 200，`PostJson` 直接 `raise RuntimeError`，根本到不了会话丢失分支。
因此诊断提示里 `KD_ACCT_ID` 应与其余三项区分表述。

#### 结论 14：`MsgCode == 1` 是干净判据（R3）

用**正确凭据**触发各类业务错误：

| 用例 | MsgCode | 消息 |
|---|---|---|
| 不存在的表单 `NO_SUCH_FORM` | **4** | 标识为“NO_SUCH_FORM”的业务对象不存在，或者被删除 |
| 不存在的字段 `FNoSuchField` | **9** | 元数据中标识为 FNoSuchField 的字段不存在 |
| 非法过滤条件 | **4** | `GetRealExpress error...` |
| 空 `FieldKeys` | **8** | data 数据包中的参数 FieldKeys 的值不能为空 |

**业务错误中 `MsgCode == 1` 的有 0 条**；14 次认证失败则**全部** `MsgCode == 1`、`ErrorCode == 500`。
判据干净，S8 可以直接采用 `MsgCode == 1`。

#### 结论 15：英文 LCID 下消息**不本地化**（R4）

`lcid=1033` 下触发认证失败，响应消息**仍是中文**「会话信息已丢失，请重新登录」，`MsgCode` 仍为 1：

```json
[[{"Result":{"ResponseStatus":{"ErrorCode":500,"IsSuccess":false,
  "Errors":[{"FieldName":null,"Message":"会话信息已丢失，请重新登录","DIndex":0}],
  "SuccessEntitys":[],"SuccessMessages":[],"MsgCode":1}}}]]
```

即 S8 担心的「英文 LCID 导致中文匹配失效」在本部署上**不成立**。
但这只是本部署的行为，`MsgCode` 仍然是更可靠的判据。

#### 结论 9：人工 Web 端登录对照（H1c）否定

用户手动用同一集成用户（`zd`）登录 K3Cloud Web 端，探针 A 每 30 秒心跳。
登录前后共 24 次心跳，A 的 SID `50917a0b` **全程未变、全部成功**；用户退出登录后同样无影响。
**交互式登录不会踢掉 WebAPI 会话**，H1c 否定。

同时用户已确认 **D1**：金蝶端「第三方系统登录授权」的指定用户登录列表**包含**该集成用户，D1 排除。

#### 结论 10：服务端不校验签名时间戳窗口，时钟漂移假设否定

把客户端 `x-api-timestamp` / `x-api-nonce` 偏移 ±1 分钟 / ±5 / ±15 / ±30 / ±60 分钟直至 **±24 小时**，
请求**全部成功**。服务端对时间戳没有窗口校验，因此客户端时钟漂移不会造成认证失败。
（`BuildHeader` 中 `nonce` 与 `timestamp` 同值这一点也顺带排除了 nonce 重放限制——
T24 的 4 路并发在同一秒内使用相同 nonce，全部通过。）

#### 由结论 8 重排的候选成因

既然是认证失败，排查方向应全部转向**认证与授权配置**，与会话生命周期无关：

| 候选 | 说明 | 本轮状态 |
|---|---|---|
| `app_id` / `app_secret` 错误或被改动 | 已实测：直接产生该错误 | ✅ 机制已确认 |
| 用户名错误 / 用户被禁用 | 已实测：直接产生该错误 | ✅ 机制已确认 |
| 用户不在「指定用户登录列表」 | 官方列出的成因 | 本账套已确认包含（D1 排除） |
| `acct_id`（账套 ID）错误 | 同类配置项，未单独实测 | 待查 |
| 第三方登录授权被禁用 / 过期 | 需在金蝶端确认 | 待查 |
| 客户端时钟漂移导致签名失效 | 服务端不校验时间戳窗口 | ❌ 已否定（结论 10） |
| 会话过期 / 多会话互踢 / 并发覆盖 | 两轮共 7 种手段全部无法复现 | ❌ 已否定（结论 5、9） |

**给报障者的最小排查清单**：核对 `KD_ACCT_ID` / `KD_USERNAME` / `KD_APP_ID` / `KD_APP_SEC` 四项与
金蝶端第三方登录授权页面是否逐字一致，以及该授权是否仍处于启用状态。这比任何会话侧的重试逻辑都有效。

#### 结论 11：T23「超时 + 抢占」组合同样无法触发（本轮最后一项）

A 建会话后闲置 **26 分钟**（00:48:46 → 01:14:51，超过官方 20 分钟会话期），
期间 B 每 2 分钟建一次同身份新会话，累计 **13 个**；随后 A 发起请求：

```
#15  01:14:51  [T23] A  A 闲置 25min 后  173ms  67577255 -> 67577255  success
```

**成功，SID 连换发都没有。** 与第 1 轮 Phase D（闲置 30 分钟时 SID 被换发）对照可知：
换发时机由服务端自行决定，且**无论换发与否，请求都成功**。「超时 + 抢占」的组合假设否定。

结果必须按“不确定操作”处理：如果 MCP Client 收到会话错误，不能直接再次保存，应先按唯一标识查询是否已经生成单据。无论实测是否出现重复单据，生产实现都不应自动重放非幂等写请求，因为测试无法覆盖所有插件、超时和事务提交时序。

### 4.4 MCP Bearer 鉴权真实客户端测试

源码 review 能确认 mcp 1.27.0 当前装配路径，但“实际客户端能否连接、错误 metadata 是否正确、升级后是否 fail-open”需要端到端测试。

| ID | 配置与操作 | 预期结果 |
|----|------------|----------|
| **T13** | streamable-http/SSE，设置正确 `MCP_API_KEY`，Client 携带正确 Bearer Token | initialize、list tools、只读 tool 调用均成功 |

### 4.7 哪些问题不需要等待真实 MCP Client 才能修复

- S2 的异常响应崩溃路径可由单元测试稳定复现。
- S4 的恢复异常覆盖原错误可用 mock SDK 测试。
- S5 的 `compare_digest`、S13 的配置解析、S19 的显式异常属于确定的本地健壮性改进。
- S1 中“不得自动重放非幂等写请求”是通用安全约束，不应以一次测试账套未产生重复单据为由保留现状。

真实 MCP Client 主要用于最终确定 S3 的正确恢复策略，以及验证 S6/S7/S12/S17 在实际传输和部署环境中的表现。S10 可以直接通过模拟较小的 monotonic 值做单元测试，不必等待真实环境。

## 6. 建议的修复顺序

（两轮实测后重排；原表的 S1、S4 已随 S3 一并解决）

| 优先级 | 条目 | 理由 |
|--------|------|------|

| 2 | **S2** ✅ 已修复 (v1.4.0) | `_check_expired` 的 `AttributeError` 崩溃路径。删除恢复机制后它仍被 `_wrap_query_result` 使用，必须修 |
| 3 | **S8** ✅ 已修复 (v1.4.0) | 判据定稿为 `MsgCode == 1`（§4.0-3 结论 14 已验证不误伤业务错误），语义正名为「无有效会话且重新认证失败」 |

| 5 | **S5** | 低成本安全硬化：恒定时间比较 |
| 6 | S9–S15 | 健壮性与一致性 |
