## 1. 起因与要回答的问题

PR #15 反馈调用 MCP 工具时出现「会话信息已丢失，请重新登录」。
`server.py` 中的 `RetryableK3CloudApiSdk` 为此实现了一套会话恢复状态机，其核心是一句注释：

```python
_RESET_COOLDOWN = 300  # seconds — new SID takes several minutes to activate server-side
```

代码 review（PR #18）指出这句话没有任何抓包、日志或实验支撑。要回答的问题依次是：

1. 新 SID 真的需要「几分钟激活」吗？→ 决定 300 秒冷却的存废
2. 「会话信息已丢失」到底怎么触发？→ 决定恢复机制该修还是该删
3. 修复要用什么判据识别这个错误？→ 决定代码怎么写

## 2. 测试环境与安全约束

这些约束贯穿三轮，换环境重跑时应当保持：

| 约束 | 说明 |
|---|---|
| **全程只读** | 统一基线请求 `BD_MATERIAL` 取 1 行、只查 `FNumber`。不碰任何写工具，不做写请求重放测试 |
| **SID 脱敏** | 只记录 `sha256(SID)[:8]`，从不打印或落盘完整 SID |
| **Cookie 脱敏** | 只记录 cookie **名称**与值长度，不记录值 |
| **凭据不落盘** | 错误凭据只在进程内内存中替换，用占位值（`__no_such_user__`、`"0"*32`），不使用任何真实的其他账号 |
| **失败认证预算** | 生产账套上重复认证失败可能触发频率限制，事先约定上限 20 次，实际用掉 14 次 |
| **会话数上限** | 官方警告过多会话会占用服务端上下文缓存，约定上限 20 个并发会话 |
| **不污染发布包** | 探针脚本一律独立于仓库代码，**不往 `server.py` 添加任何诊断钩子** |
| **人工操作不代做** | 涉及 Web 端登录的对照测试由用户手动完成，测试方不接触登录凭据 |

## 3. 探针方法论

三个独立脚本，均直连 SDK 而不经过 MCP 层。**这是关键的方法选择**：冷却期与恢复逻辑
全部位于 `RetryableK3CloudApiSdk.Execute`，MCP 层只是它的调用者——透过 MCP 工具接口既
无法注入过期 SID，也看不到 SID 状态和被丢弃的第二次响应，只能观察到黑盒的「查询失败」。

### 3.1 四个使实验成为可能的技术点

**① `cookiesStore` 可整体替换** —— `WebApiClient.__init__` 无条件设置 `self.cookiesStore = CookieStore()`，
是普通实例属性。而 `CookieStore.set_sid()` 只在新值非空时覆盖、**永不清空**，所以清除 SID 的唯一办法
就是整体替换：

```python
from k3cloud_webapi_sdk.model.cookie_store import CookieStore
sdk.cookiesStore = CookieStore()      # 清空 SID 与 cookies
sdk.cookiesStore.SID = "invalid-xxx"  # 或注入任意 SID
```

**② `identify` 可原地改凭据** —— `sdk.identify` 是 `Identify` 实例，属性可变。
这让「**同一实例、同一 SID，只换凭据**」的 A-B-A 对照成为可能，是第 3 轮修正结论的关键：

```python
snap = {k: getattr(sdk.identify, k)
        for k in ("DCID", "UserName", "AppId", "AppSecret", "LCID", "OrgNum")}
sdk.identify.AppSecret = "0" * 32     # 只改凭据，不动 cookiesStore
# ... 发请求 ...
for k, v in snap.items():
    setattr(sdk.identify, k, v)       # 复原
```

**③ HTTP 层观测靠 monkeypatch** —— `PostJson` 直接调模块级 `requests.post`，不暴露 response 对象。
包一层即可拿到状态码、响应头、节点标识，且不改动 SDK 与 `server.py`：

```python
import k3cloud_webapi_sdk.core.webapi_client as wc
_orig = wc.requests.post
def _patched(*a, **kw):
    res = _orig(*a, **kw)
    record(status=res.status_code, headers=res.headers)   # 只记名称与状态，不记值
    return res
wc.requests.post = _patched
```

**④ 用原生 `K3CloudApiSdk`，不用 `RetryableK3CloudApiSdk`** —— 否则恢复逻辑会把现象掩盖掉。
同时**复用 `server.py` 的 `_check_expired` 做分类**，等于每次请求都在拿真实响应校验生产代码的检测器。

### 3.2 每次请求统一记录的字段

序号 · 时刻 · 测试项 · 实例标签 · 耗时 ms · 请求前 SID 摘要 · 请求后 SID 摘要 · 是否换发 ·
结果分类（success / session_lost / biz_error / exception）· `MsgCode` · `ErrorCode` · 消息前缀 ·
HTTP 状态 · 请求是否携带 `kdservice-sessionid` · `Set-Cookie` 名称 · 节点标识

### 3.3 多会话与并发的实现方式

同一进程内建多个彼此独立的 `K3CloudApiSdk` 实例即可——每个实例有自己的 `cookiesStore`，
发出的是独立 HTTP 请求，**服务端无从区分是否同进程**。真并发用 `threading.Barrier` 让 N 个线程
在同一毫秒发出请求，比多进程编排简单得多，效果等价。

## 4. 第 1 轮：会话生命周期（2026-08-28）

**要回答**：新 SID 需要「激活时间」吗？

| # | 阶段 | 操作 | 耗时 | SID 前 → 后 | 结果 |
|---|---|---|---|---|---|
| 1 | A | 空 SID 首请求 | 405ms | `<empty>` → `8d74d3ba` | 成功 |
| 2 | B | 注入无效 SID（`invalid-<uuid4>`） | 308ms | `669f30c9` → `8c699350` | 成功，服务端换发新 SID |
| 3–6 | C0 | 复用刚下发的新 SID，t=0/1/5/30s | 176–1059ms | `8c699350` 全程不变 | 全部成功 |
| 7 | C | 整体替换 `cookiesStore` 后 t=0 | 1496ms | `<empty>` → `1c1857a2` | 成功 |

**Phase D — 自然过期对照**（每轮闲置 1800s，期间不发任何请求）：

| # | 操作 | SID 前 → 后 | 结果 |
|---|---|---|---|
| 1 | 取真实 SID（预热） | `<empty>` → `ff5097a3` | 成功 |
| 2 | 闲置 1800s 后 | `ff5097a3` → `b702054e` | 成功（静默换发） |
| 3 | 闲置 3600s 后 | `b702054e` → `b702054e` | 成功（未换发） |
| 4 | 闲置 5400s 后 | `b702054e` → `ede9d3a9` | 成功（再次换发） |

### 结果

- **「新 SID 需要几分钟激活」证伪**：新 SID t=0 即可用，此后 1/5/30 秒摘要不变、连续成功。
  **300 秒冷却没有事实依据。**
- 空 SID、无效 SID 都不会让请求失败；服务端忽略无效 SID 并换发新的。
- 累计闲置 90 分钟**一次都没复现**「会话信息已丢失」。SID 换发时机由服务端自定，
  但**换与不换，请求都成功**。
- ⚠️ **本轮的方法缺陷**（第 3 轮才暴露）：注入的是**随机无效 SID**，服务端从没见过，
  当作"没有会话"直接建新的。这覆盖不到"服务端已知且已失效"的会话。

## 5. 第 2 轮：并发抢占假设（2026-08-29）

**要回答**：是不是另一个程序/用户用同一授权身份重新认证，把先前的会话踢掉了？

这个假设有分量，因为**本项目的默认部署形态天然制造多会话**：stdio 传输下每个 MCP Client
各自启动一份 server 进程，各自建独立会话，却共用同一个 `KD_USERNAME`/`APP_ID`。

| 测试 | 干预 | 请求数 | 会话丢失 | SID 换发 |
|---|---|---|---|---|
| 控制相 | A 单独活跃 5 次 | 5 | 0 | 0 |
| T21a | A、B 两个稳定会话交替 10 轮 | 20 | 0 | 0 |
| T22 | 另建 18 个同身份会话，累计 2/5/10/14/18 各检查一次 A | 23 | 0 | 0 |
| T24 | 4 个会话线程级真并发 × 15 轮 | 60 | 0 | 0 |
| T25 | 人工 Web 端登录 + 登出，A 每 30s 心跳 20 分钟 | 40 | 0 | 0 |
| T23 | A 闲置 26 分钟，期间插入 13 个同身份新会话 | 15 | 0 | 0 |
| 时钟偏移 | `x-api-timestamp` 偏移 ±1min ～ **±24 小时** | 11 | 0 | — |
| **凭据错误对照** | 不存在的用户名 / 错误的 `app_secret` | **2** | **2** | — |

### 结果

- **H1a（会话池挤占）、H1b（单会话踢下线）否定**：同一授权身份可同时持有至少 20 个互不干扰的会话。
- **H1c（交互式登录踢会话）否定**：用户手动登录/登出 Web 端，A 的 SID `50917a0b` 40 次心跳全程未变。
- **进程内并发覆盖排除**：4 路真并发无异常；且 mcp 1.27 的同步 tool 直接在事件循环中执行，本就串行。
- **时钟漂移假设否定**：服务端**不校验** `x-api-timestamp` 窗口，±24 小时照样放行。
  （`nonce` 与 `timestamp` 同值也顺带排除了 nonce 重放限制——T24 同一秒内 4 个相同 nonce 全通过。）
- **D3（LB 节点粘性）无适用条件**：响应头只有 `Server: Microsoft-IIS/8.5`，无 `ARRAffinity`/`BIGipServer*`
  一类亲和性 cookie。**但这意味着多节点环境会有本部署测不出的行为。**
- **唯一能产生该错误的是把凭据改错。** 这条对照本是为了排除干扰项而做的，结果成了突破口。

### 附带发现：SDK 的 Set-Cookie 解析不符合 RFC

`FillCookieAndHeader` 用 `headers['Set-Cookie'].split(',')` 切分，而 cookie 的 `expires` 值
本身含逗号（`Thu, 28-Aug-2026 ... GMT`）。实测服务端实际存下的是：

| 存储 key | `name` | `path` |
|---|---|---|
| `'kdservice-sessionid'` | `'kdservice-sessionid'` | `''`（丢失） |
| `' ASP.NET_SessionId'` | `' ASP.NET_SessionId'`（**带前导空格**） | `''`（丢失） |

回带头为 `Theme=standard;kdservice-sessionid=…; ASP.NET_SessionId=…`，在本部署上**碰巧可用**——
名字里的前导空格恰好充当了 RFC 6265 要求的 `; ` 分隔空格。属上游 SDK 缺陷，本项目无法直接修复。

## 6. 第 3 轮：认证模型（2026-08-30）

**要回答**：第 2 轮的凭据结论只有 2 次请求，且用的都是空 SID 实例——它可重复吗？适用条件是什么？
修复要用的判据可靠吗？

### R5 / R1 — SID 与凭据的优先级（A-B-A 对照）

| 步骤 | 状态 | 结果 |
|---|---|---|
| ① 好凭据建会话 | SID 已建立 | 成功 |
| ② **改坏 `app_secret`，保留 SID** | 坏凭据 + 有效 SID | **成功** ← 关键 |
| ③ **清空 `cookiesStore`**，凭据仍坏 | 坏凭据 + 空 SID | **会话信息已丢失** |
| ④ 复原凭据，SID 仍空 | 好凭据 + 空 SID | 成功 |

R1 以 3+3+3 次请求复核步骤 ②：持有有效 SID 时把 `app_secret` 换成 32 个 `0`，**连续 3 次全部成功**。

### R2 — 凭据字段矩阵（全新实例 / 空 SID，各 3 次）

| 字段 | 结果 | MsgCode |
|---|---|---|
| `KD_USERNAME` | 会话信息已丢失 ×3 | 1 |
| `KD_APP_ID` | 会话信息已丢失 ×3 | 1 |
| `KD_APP_SEC` | 会话信息已丢失 ×3 | 1 |
| `KD_LCID`（无效值 9999） | 会话信息已丢失 ×3 | 1 |
| `KD_ORG_NUM`（999999） | **成功** ×3 | — |
| `KD_ACCT_ID` | **HTTP 非 200 → `RuntimeError`** ×3，`Fail to verify thirty passport` | — |

### R3 — `MsgCode` 假阳性检查（正确凭据 + 错误查询参数）

| 用例 | MsgCode | 消息 |
|---|---|---|
| 不存在的表单 `NO_SUCH_FORM` | **4** | 标识为“NO_SUCH_FORM”的业务对象不存在，或者被删除 |
| 不存在的字段 `FNoSuchField` | **9** | 元数据中标识为 FNoSuchField 的字段不存在 |
| 非法过滤条件 | **4** | `GetRealExpress error...` |
| 空 `FieldKeys` | **8** | data 数据包中的参数 FieldKeys 的值不能为空 |

### R4 — 英文 LCID 对照

`lcid=1033` 下触发认证失败，消息**仍是中文**「会话信息已丢失，请重新登录」，`MsgCode` 仍为 1。

### 结果

- **服务端认证优先级：SID 对应有效会话时放行、不校验凭据；否则回落到凭据校验。**
  （本轮 R5 的措辞是「有 SID 就放行」，2026-08-30 补充实测把它修正为「**对应有效会话的** SID」——
  认证失败时服务端也会下发 SID，但那是空壳，见 §7。）
- 该错误的准确含义是「**没有有效会话，且重新认证也失败**」，14/14 可重复复现。
- `MsgCode == 1` 是**干净判据**：业务错误的 MsgCode 是 4/9/4/8，无一为 1。
- `KD_ACCT_ID` 错误走**完全不同的路径**（HTTP 非 200 → `RuntimeError`），到不了会话丢失分支。
- `KD_ORG_NUM` 参与签名但服务端不校验其有效性。
- `_check_expired` 对全部 14 次真实认证失败响应**判定正确**，未崩溃。

## 7. 最终结论：服务端的认证模型

```
请求到达
  ├─ 携带的 SID 对应一个有效会话？
  │   ├─ 是 ─→ 放行，**不校验签名/凭据**
  │   └─ 否（无 SID / 已失效 / 认证失败时拿到的空壳 cookie）
  │        └─→ 校验 HMAC 签名与凭据
  │              ├─ 通过 ─→ 建立会话、下发 SID、请求成功（对调用方完全无感）
  │              └─ 失败 ─→ 「会话信息已丢失，请重新登录」(MsgCode=1)
  │                          ※ 此时服务端**仍会下发一个 SID**，但它是空壳，
  │                            带着它的后续请求同样回落到凭据校验
  └─ acct_id 错误 ─→ HTTP 非 200「Fail to verify thirty passport」→ SDK 抛 RuntimeError
```

### 补充实测（2026-08-30，修正结论 12 的表述）

| 观察 | 结果 |
|---|---|
| 有有效会话时连续 3 次调用 | SID 全程不变，**不重新登录** |
| 坏凭据时连续 3 次调用 | 每次都**真实地重新认证并真实失败**；首次失败时服务端仍下发了 SID（空壳） |
| 把凭据改回正确（**不重启、不清 cookie**） | **下一次调用立刻成功**，且沿用那个空壳 SID |

因此「有 SID 就放行」的说法不够准确，应为「**SID 对应有效会话时**才放行」。
两个直接推论：

1. 认证失败**不会锁死**——每次请求都在用当前内存中的凭据重新尝试；
2. **修复金蝶端配置（重新启用授权、把用户加回登录列表）无需重启 MCP Server**，
   下一次调用自动恢复；只有改 `.env` 的值才必须重启（`.env` 仅在启动时读取一次）。

**「会话信息已丢失」是一句严重误导的错误文案**：它讲的不是会话过期，而是**认证失败**。
真正的会话过期在这个部署上是**完全无感**的——服务端会静默换发新 SID，请求照常成功。

### 一条必须记住的运维含义

凭据/授权一旦出错，会被一个**仍然有效的 SID 长期掩盖**，直到会话失效或进程重启才突然爆发。
这解释了「昨天还好好的、代码一行没改就坏了」这种间歇性表现，也意味着
**「重启一下 MCP Server」不但不能修复，反而会把偶发问题变成永久问题**（新进程没有 SID，必须走凭据校验）。

## 8. 对代码的直接影响

| 结论 | 对应改动 |
|---|---|
| 恢复机制没有任何一种情形能帮上忙 | **删除整个 `RetryableK3CloudApiSdk` 恢复流程**：`_RESET_COOLDOWN`、`_session_reset_at`、`cookiesStore` 重置、第二次 `super().Execute()` |
| S1（写请求重放）、S4（恢复异常顶替原始错误） | 随恢复机制删除**一并消失**，无需单独修 |
| `MsgCode == 1` 判据干净 | 以它为唯一主判据，消息串仅作日志佐证 |
| 判据语义正名 | 从「会话过期」改为「**无有效会话且重新认证失败**」 |
| 字段矩阵 | 诊断提示列 `KD_USERNAME` / `KD_APP_ID` / `KD_APP_SEC` / `KD_LCID`，`KD_ACCT_ID` 单列说明 |
| 现有测试 | 删除围绕冷却期的测试与「第二次成功仍返回第一次错误」的断言，改为断言「错误原样透传且不产生第二次请求」 |

`tests/test_server.py` 的 `_EXPIRED_DICT` fixture 与真实响应**完全一致**（含 `MsgCode: 1`），无需调整。

| `MsgCode == 1` 会误伤业务错误 | 第 3 轮 R3：业务错误为 4/9/4/8 |
| 英文 LCID 导致中文匹配失效 | 第 3 轮 R4：消息不本地化（**换环境需重测**） |

## 10. 局限

必须写明，避免把本文结论当成普适事实：

1. **只覆盖一个部署**：单节点 IIS 8.5、内网穿透、单一 K3Cloud 版本。多节点/LB 环境、
   不同产品版本或补丁，都可能有本文测不出的行为。表中标注「换环境需重测」的两条尤其如此。
2. **拿不到报障者的环境信息**，无法确认 PR #15 的具体成因就是本文定位的认证失败；
   只能说该错误在本部署上**唯有**认证失败一种成因。
3. **未测写操作重放**（review 中的 T12）。生产账套上不做，结论中「不得自动重放非幂等写请求」
   是通用安全约束，不依赖实测。
4. **失败认证只做了 14 次**，未探到频率限制或锁定阈值——也不建议去探。

## 11. 复现指南

探针脚本按安全约束留在临时目录、未纳入仓库。重建只需三个文件，要点已在 §3 给出：

| 脚本 | 作用 | 关键点 |
|---|---|---|
| `probe_session.py` | 第 1 轮：会话生命周期 | `cookiesStore` 替换与 SID 注入（§3.1 ①） |
| `multi_session_probe.py` | 第 2 轮：多会话与并发 | 多实例 + `threading.Barrier`（§3.3）、HTTP 层 monkeypatch（§3.1 ③） |
| `auth_probe.py` | 第 3 轮：认证模型 | `identify` 原地换凭据（§3.1 ②）、`MsgCode` 提取 |

共同要素：从项目外的 `.env` 加载凭据（值不进日志）、统一 `BASELINE` 只读查询、
复用 `server.py` 的 `_check_expired` 做结果分类、SID 一律 `sha256[:8]`。

换环境重跑时的最小集合：**第 1 轮 Phase A/B/C0 + 第 3 轮 R5/R3**。
前者判断 SID 是否需要激活，后者确定认证优先级与判据是否仍然干净——
这五项覆盖了所有直接影响代码的结论，约 20 次请求即可完成。
